# 插件平台语义交互与状态规则

> 日期：2026-09-10 · 状态：设计决定已确认，尚待实施。
> 依据：[架构演进](./plugin-platform-evolution.md)、[ADR-0003](./adr/0003-semantic-action-responsibilities.md) 与 [ADR-0006](./adr/0006-presentation-state-and-result-ownership.md)。本文记录第二轮讨论确认的六项建议，不替代现行 schema、UiKitAdapter 或架构检查。

## 1. 记住用户的工作，按作用域恢复

宿主保存草稿和有意义的浏览位置，按工作区、会话与 contribution 的适用作用域隔离。例如工作区 A 的文件选择不能带入工作区 B；返回 A 时可以恢复 A 的选择。

| 状态 | 换 renderer/布局 | 工作区往返 | 应用重启 |
| --- | --- | --- | --- |
| 未提交的输入草稿 | 保留 | 保留 | 保留 |
| 当前文件选择 | 保留，目标须有效 | 保留，目标须有效 | 允许恢复，先检查目标 |
| 详情目标与返回位置 | 保留，目标须有效 | 保留，目标须有效 | 允许恢复，先检查目标 |
| 键盘焦点 | 尽量恢复同一语义目标 | 恢复有效目标或合理入口 | 不要求原样恢复 |
| 悬停与动画进度 | 不保留 | 不保留 | 不保留 |

文件删除、贡献停用或上下文失效时，返回合理入口，不把旧目标静默替换成另一个业务对象。瞬时状态属于 renderer；恢复状态中不保存 DOM 节点或组件实例。这样既避免换 UI 清空用户工作，也不要求宿主同步每个动画细节。

具体存储键、窗口间共享/隔离、保存时机、保留期限、草稿格式升级及目标失效后的具体入口仍待实现设计；本轮不默认多个窗口共享同一份导航。

## 2. 一个用户意图可以串联三类动作

以点击 `App.svelte` 查看差异为例：renderer 立即反馈选择；UI 向宿主提交“查看该文件差异”的语义意图与上下文；宿主验证、维护导航并调度能力；Git 能力返回数据；renderer 决定使用中央区域还是窄屏详情页。

动作合同区分本地交互、宿主导航、能力调用，但一次用户操作可以串联它们。插件不能要求打开某个物理面板或指定尺寸，renderer 不能绕过宿主调用任意 IPC。这样业务操作和布局可以分别变化。

完整消息至少需要能表达动作身份、业务目标、上下文及适用的版本/代际信息；最终字段名、三类消息如何组合以及关联 ID 的结构在 P1 冻结，不将此处叙述作为已发布 wire protocol。

## 3. 只读浏览以最新有效意图为准

用户先点 A 再点 B，B 查询先返回、A 后返回时，页面必须继续显示 B。取消 A 是优化；拒绝 A 覆盖当前视图是必需行为，不能以取消成功作为正确性的前提。

| 操作类别 | 结果接纳规则 |
| --- | --- |
| 只读查询 | 仅与当前有效查询意图匹配的结果可更新当前视图；过期结果不得覆盖 |
| 导航 | 以该导航上下文的最新有效意图为准，不让迟到响应倒退用户位置 |
| 写入 | 独立跟踪执行结果；不能因为切换页面或选择就丢弃结果或盲目重试 |

“最新”只在相应视图/导航上下文内比较，不用一个全局序号淘汰所有工作区的请求。具体请求关联方式仍待冻结。P1 覆盖只读与导航，P2 验证 renderer 切换；P4 完善写入取消、冲突与结果未知的处理。

## 4. 旧页面发来的动作要重新验证

宿主在动作提交时验证上下文身份、数据 revision、运行实例 generation，以及适用的 presentation generation 和权限。它们分别防止跨工作区误用、基于旧数据操作，以及旧进程/旧 renderer 的迟到消息污染新实例；这些身份不能互相替代。

过期动作不静默改目标执行。只读动作可以要求刷新或重新读取，但仍须通过当前身份与授权检查；写入必须重新验证目标、条件与权限仍有效，必要时重新取得确认，不能沿用已失效的操作依据。是否需要用户再次确认由最终审批合同确定。

哪些数据变化使哪些动作失效、revision 的粒度、具体错误码以及刷新后是否自动继续，仍在 P1/P4 相应合同中确定。

## 5. 统一操作含义，允许控件使用标准交互方式

不同 renderer 必须提供相同的业务操作、状态含义与可访问入口。表格和卡片可以使用符合各自控件模式的键盘行为，不要求物理按键路径完全相同；标准模式中的 Tab、方向键、Enter/Space 等应让用户能发现、选择和激活动作，且不产生键盘陷阱。

交互合同必须写清焦点的合理去向、loading/disabled 含义、错误与目标的关联以及重试入口。具体选择键/激活键、详情返回焦点、加载时可用动作由 P1 根据控件模式冻结，通过同一组操作场景验收。这样保留操作语义的一致性，也不迫使所有 UI 使用同一种控件。

## 6. 分页与不完整内容必须可表达

P1 合同必须能表达集合分页/逐步加载及 diff 内容不完整。用户必须能够区分完整结果与只显示一部分的结果；大文件不能静默截断后伪装成完整内容。

每页数量、响应/文档/字段大小上限、diff 分段或截断方式、继续读取机制，通过实际样本验证后在 P1 验收前冻结。先确定这些状态可以被表达，使 renderer 不会把所有结果都当成一次性完整数据；不在本轮猜定数值。

## 验收场景与阶段

以下均为待实施项，决定被接受不等于验收已通过。

- [ ] P1：A/B 查询逆序返回、旧请求取消失败时，当前页面仍展示 B。
- [ ] P1：切换工作区、文件删除、数据 revision 失效后，旧动作被拒绝或进入明确刷新流程，不误开其他目标。
- [ ] P1：大集合和大 diff 明确呈现分页/部分内容；超限样本受控处理。
- [ ] P1：两种布局 × 两套皮肤及第二最小 renderer 保留相同语义动作；按各控件标准模式完成选择、打开、返回、错误重试，并验证焦点及可访问性。
- [ ] P2：换布局/renderer 与工作区往返保留草稿和有效浏览位置；应用重启恢复草稿，恢复浏览位置前检查目标；瞬时状态无需还原。
- [ ] P2：旧 renderer 消息不污染新实例，多个作用域的请求不会互相淘汰。
- [ ] P4：写入开始后切换页面，仍能追踪真实执行状态；超时或失联不伪装成失败，也不盲目重试。
