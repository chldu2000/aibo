# 事件按业务用途保留，搜索投影与原始记录分离

2026-10-27 决定：SQLite 继续持有业务历史、关键操作事实和恢复数据；事件是否持久化、保留多久以及是否参与全文搜索是三个独立决定。不能将所有协议通知视为永久业务历史，也不能因为数据库体积大而删除仍被历史、审批或恢复读取的事件。

本机诊断时约 8.74 GB 数据库中，全文索引占 4.71 GB、搜索副本占 1.62 GB；约 211 万条搜索文档中的 209 万条来自能力调用及事件。完整事件 JSON 同时存在于审计表、搜索正文和 trigram 索引，使重复观察被多次放大。将同样内容迁移到日志文件或另一个数据库不能解决保留范围问题。

业务历史随会话保留；授权及副作用记录保留操作、身份、依据和结果；恢复记录保留到恢复责任结束；诊断过程采用有界保留；重复观察优先保存最新状态、变化和聚合统计。分类依据宿主验证的合同及操作语义，不按插件名称分类，不将声明 read 等同于没有恢复或审计价值。旧记录缺少分类证据时保持保留。

## 首批实施与限制

0066 只收窄可重建搜索投影：能力调用保留一条可搜索摘要，完整能力事件仍从既有审计接口读取，不再复制到搜索文档或建立全文索引。主会话、工具输出、子代理最新消息、附件、文件、工程任务和工作区操作的既有搜索保留。窗口所有权与作用域隔离保持不变。

此次不启用按时间删除原始事件，也不将建议过的 7/30 天当作已批准的保留期限。当前子代理历史、分叉、审批校验、上下文重置和序号分配仍依赖 agent_events，能力审计使用 capability_events 的持久游标。取消这些依赖前，业务读取必须拥有独立且可靠的记录，并明确清理后的游标语义。具体条件见[存储策略](../event-storage.md)。

原始事件与业务投影的事务一致性、先提交再通知界面的顺序不变。不采样授权或副作用事实，不清理活动/结果未知操作，不以已投递到界面作为持久化成功的替代证据。

## 迁移代价

追加迁移事务内删除派生搜索副本并重建 FTS，保留原始表及已有迁移 checksum；失败整体回滚。首次升级需要扫描剩余搜索文档并产生 WAL，应在发布前测量大库升级。删除释放的页可被 SQLite 重用，文件不会自动等量缩小；不在启动路径运行 VACUUM。物理压缩属于独立维护操作，需可恢复备份、足够空间与独占维护窗口。
