# Aibo 本地诊断日志规格

状态：L1 已接入，验收中。版本：1。日期：2026-10-12。本文定义行为与验收要求；实际命令、结果与尚未完成的门槛见[实施与验收记录](diagnostic-logging-validation.md)，不得将矩阵本身视为已经通过的测试证据。

## 目标与交付范围

发生启动失败、插件退出、会话调用失败或界面异常时，用户应能从本地日志确定应用版本、失败阶段、错误类别和相关运行身份。日志必须有容量上限，且写入故障不能成为应用或会话失败的原因。

第一阶段 L1 必须交付：宿主结构化日志、启动与退出、Rust panic、插件生命周期、会话关键失败、前端异常、轮转与清理，以及设置中的日志状态和打开目录入口。L1 全部验收通过后，才可称为“支持保存诊断日志”。

第二阶段 L2 增加：30 分钟临时诊断模式、按时段导出诊断包。L2 是后续交付，不是 L1 的验收前提；L1 界面不显示尚未实现的操作。聊天、执行历史和 artifact 继续采用现有存储合同；日志不承担恢复或执行授权职责。

## 当前基线与约束

- [宿主入口](../src-tauri/src/lib.rs) 目前使用 tracing 标准输出，在 setup 中打开 SQLite、恢复状态并装配插件。文件日志必须覆盖这些初始化步骤。
- [存储选择](../src-tauri/src/app_storage.rs) 已区分正式数据目录与 development 子目录，日志沿用这一选择结果。
- [插件进程](../src-tauri/src/plugin_runtime.rs) 当前读取并丢弃 stderr；L1 记录宿主观察到的生命周期，保持原始 stderr 不落盘。
- [任务输出脱敏](../src-tauri/src/artifact.rs) 只处理部分关键词，不能用它证明任意诊断文本可安全保存。
- [UI 架构](ui-architecture.md) 已有固定宿主“运行与诊断”设置页；日志入口放在此处，不归外部呈现插件所有。
- [宿主与插件边界](plugin-boundaries-and-regression.md) 要求终端正文不进入原生日志。新诊断路径也必须遵守。

## 事件与记录时机

以下名称是稳定事件代码。可增加兼容事件，但不得通过自由文本代替表中的事件，也不得依赖日志内容决定业务状态。

| 要求 | 事件 | 级别与触发条件 | 允许的附加信息 |
| --- | --- | --- | --- |
| LOG-01 | app.starting、app.ready、app.stopped | INFO；进程开始、原生与必要前端初始化完成、正常结束 | 应用版本、构建渠道、系统类型与架构、启动 ID、各阶段耗时；不含用户名和设备名 |
| LOG-02 | startup.stage_completed、startup.failed | 阶段成功 INFO，失败 ERROR；覆盖数据库打开与迁移、插件恢复与注册、会话恢复、宿主装配 | 固定阶段代码、耗时、错误分类；失败不产生 app.ready |
| LOG-03 | app.previous_exit_unknown | WARN；发现已经结束且没有正常结束证据的先前运行 | 前次启动 ID；只能称为“上次未正常结束”，不能推断一定发生崩溃 |
| LOG-04 | app.panic | ERROR；进入 Rust panic hook | 安全的宿主源码位置与允许的堆栈帧；不保存 panic 原始 payload |
| LOG-05 | plugin.starting、plugin.ready、plugin.start_failed、plugin.stopped、plugin.exited_unexpectedly | 正常生命周期 INFO；启动失败或意外退出 ERROR | 安装 ID、插件 ID 与版本、贡献 ID、runtime generation、退出码或信号、耗时、失败阶段 |
| LOG-06 | plugin.request_failed、plugin.protocol_rejected | WARN；超时、断开、无效响应或合同不匹配 | 宿主请求 ID、操作类别、错误码、期望合同版本、耗时；不保存请求或响应正文 |
| LOG-07 | session.operation_completed、session.operation_failed、session.recovery_completed | 完成或恢复 INFO，失败 WARN；创建、恢复、发送、取消、关闭的关键边界 | 会话 ID、回合 ID、宿主请求 ID、generation、固定操作及结果代码、耗时 |
| LOG-08 | frontend.exception、frontend.unhandled_rejection、presentation.failed | ERROR；可信前端未捕获异常、未处理拒绝、宿主已观察到的呈现加载或运行故障 | 宿主窗口 ID、来源类别、安全资源名和行列位置、已分类的原因；不保存任意异常 message 或 rejection 对象 |
| LOG-09 | diagnostics.dropped、diagnostics.write_failed、diagnostics.recovered | WARN、ERROR、INFO；日志被丢弃、文件写入失败、写入恢复 | 丢弃条数、原因代码、首次发生时间、恢复时间；不可递归调用失败的写入路径 |

LOG-05 的主动停用、替换或关闭必须标记为预期停止。相同能力的内置和第三方插件走相同路径，不能以插件名称决定日志行为。插件启动时尚未关联会话，允许没有 session_id。

LOG-07 记录宿主实际观察到的操作结果。请求返回仅代表请求完成，不能伪造回合已完成或远端已执行；取消已请求、已确认、结果未知使用不同结果代码。流式 token、心跳、轮询成功和每个 UI 点击不作为 INFO 事件。

不为日志重复执行健康检查、登录、恢复或数据库查询。不改动会话绑定、generation 校验、投递证据、审批记录和恢复顺序。权限及审计的完整记录继续由现有业务存储负责。

## 记录结构

LOG-10：磁盘文件为 UTF-8 JSONL，每条记录占一行，使用 LF 结束，无 ANSI 控制序列。首版 schema 值为 aibo.diagnostic/v1。记录包含：

| 字段 | 规则 |
| --- | --- |
| schema、timestamp、level、event、component | 必填；时间采用 UTC RFC 3339 毫秒；级别为 INFO、WARN、ERROR，L2 允许 DEBUG |
| boot_id、pid、sequence | 必填；每次进程启动生成新的 boot_id；sequence 在本次进程中单调递增，允许因丢弃出现间隙 |
| app_version、build_channel、os、arch | 每条记录必填，包括应急记录；来自宿主构建信息及固定平台枚举，同一 boot_id 内保持不变，不接受前端或插件覆盖 |
| elapsed_ms | 必填；由单调时钟计算，系统时钟回拨不产生负值 |
| session_id、turn_id、request_id、installation_id、plugin_id、contribution_id、generation_id、window_id | 仅在相关且已由宿主确认时填写；未知值省略，不填写虚构身份 |
| operation、outcome、stage、error_code、duration_ms、exit_code、signal、count | 只用于事件允许的语义；枚举采用固定代码，数值检查范围 |
| frames | 仅异常事件允许；最多 20 帧，仅含经过验证的资源或模块名与行列信息 |

应用版本、构建渠道、系统类型与架构作为所有事件的公共字段随每条记录保存，不仅保存在 app.starting 中；宿主在日志初始化时取得并缓存这些受控值，应急通道读取它们不增加文件 IO 或锁依赖。这些字段一并计入单条记录、分片和总容量限制。即使包含 app.starting 的分片已按年龄或容量清理，或导出时排除了启动时段，每条保留的完整记录仍可独立确定运行环境，无需保留启动分片或额外元数据文件。

不同进程的日志使用 boot_id 区分运行归属，每个文件名包含启动 ID；不能从启动 ID 推断应用版本，也不能用当前进程的版本补写历史记录。固定事件代码与业务诊断字段不随界面语言改变，状态页文案提供中英文。

单条记录连同换行最多 16 KiB，单个字符串最多 256 个 UTF-8 字节。超限的可选字段在字符边界截断或省略，设置 truncated=true；枚举或身份字段非法时省略并增加受限的 rejected_fields 计数，不能截断后冒充另一个身份。未知字段丢弃，不能存在任意对象或自由文本 passthrough。

示例只说明格式，不表示实际故障：

```json
{"schema":"aibo.diagnostic/v1","timestamp":"2026-10-12T08:00:00.000Z","level":"WARN","event":"plugin.request_failed","component":"plugin_runtime","boot_id":"01ARZ3NDEKTSV4RRFFQ69G5FAV","pid":1234,"sequence":42,"app_version":"0.0.0","build_channel":"development","os":"windows","arch":"x86_64","elapsed_ms":30125,"session_id":"01ARZ3NDEKTSV4RRFFQ69G5FAW","request_id":"01ARZ3NDEKTSV4RRFFQ69G5FAX","operation":"session.resume","error_code":"timeout","duration_ms":30000}
```

不同进程之间不保证全序。阅读器以 boot_id、sequence 判断同一次运行的次序，不能仅按墙钟时间排列后推断因果。正常关闭后的文件每一行都必须可解析；被强杀后的最后一行允许不完整，读取与导出时只忽略这一不完整尾行。

## 内容限制与边界验证

LOG-11：事件在序列化、排队和写入前完成字段选择与净化。应用文件 sink 只接收受控诊断事件；不能把现有所有 tracing 事件及其 %error、?payload 字段直接接到文件。已有输出中的绝对数据库路径和任意错误文本须经同一边界处理后才能进入新日志。

任何级别都不允许保存认证令牌、Cookie、Authorization、API key、密码、环境变量值、命令参数、聊天或推理正文、附件和文件内容、完整 SQL 参数、原始协议包、工具或终端 stdout/stderr。不能依靠提高日志级别、RUST_LOG 或开启 L2 来解除限制。

记录 OS 错误类别和数字错误码，数据库错误使用固定分类及迁移版本，不直接序列化 Display/Debug 错误链。插件错误映射为宿主允许的代码，未知值为 unclassified。未经验证的插件提交字段不能成为本地相关身份。

绝对用户目录和工作区路径默认不落盘。确有需要时以受控角色名（app_data、workspace、plugin_package）说明对象，或使用宿主 ID。堆栈只保留已确认的应用资源名及行列；删除消息行、URL 查询与片段、绝对路径及未知外部资源。无法安全保留的帧省略。

LOG-12：前端只可通过受限诊断 IPC 上报固定事件类别，原生侧重新校验字段、大小和速率，并从调用窗口取得身份；前端不能选择写入路径、日志级别、任意会话归属或原生事件名称。仅可信宿主窗口可调用；外部呈现与独立工具页不得取得新通用写文件权限。呈现故障由已有可信桥报告，不要求插件提交日志正文。

文件默认仅面向当前用户：Unix 新建目录 0700、文件 0600；Windows 使用当前用户应用数据目录的 ACL，不能主动放宽权限。日志只在本地保存，无自动上传。恶意修改日志目录为符号链接或 junction 时须拒绝写入或清理到所选应用数据范围之外，并报告不可用。

## 保存与清理

LOG-13：由 app_storage::data_dir 选择的目录记作 DATA。正式版写 DATA/logs/；开发版所选 DATA 已含 development，因此结果为应用数据目录/development/logs/，不能重复追加 development。日志代码不接受工作区或插件指定的根目录。

文件命名为 aibo-YYYY-MM-DD-BOOT_ID-NNNN.jsonl，日期为 UTC，分片序号递增。每个进程只写自己的分片，重启生成新 boot_id；同日重启不覆盖旧日志。

| 配置 | L1 固定默认值 | 规则 |
| --- | --- | --- |
| 单文件上限 | 10 MiB，即 10 × 1024 × 1024 字节 | 写入下一条完整记录前检查，超限则先换文件，不拆分记录 |
| 按日轮转 | UTC 日期变化 | 下一条事件写入新分片；日期回拨也创建新分片，绝不覆盖原文件 |
| 保留时间 | 14 × 24 小时 | 以封存时间计算；启动及运行中每 60 秒检查，到期分片删除 |
| 总容量 | 100 MiB，即 100 × 1024 × 1024 字节 | 当前与封存的诊断 JSONL、应急记录一并计入；写入前清理旧分片 |
| 应急容量 | 总容量内预留 64 KiB | 用于最小 panic/终止诊断；不是上限之外的额外文件 |

LOG-14：清理按封存时间从旧到新进行，时间相同以文件名排序。只处理本功能拥有且验证格式的普通文件，不能递归删除、跟随链接或触碰 SQLite、artifact、插件数据及未知文件。超过 14 天与超过容量任一条件成立即可清理。

多进程写入和清理需协调同一 profile 的容量；不能删除仍在写入的分片。若所有可删除旧分片清完后仍不足，停止接受磁盘记录并报告 quota_exhausted，禁止无限增长或通过删除另一活动进程文件腾空间。删除被拒绝时采用相同行为，允许实际占用因外部写入或历史文件暂时超限，但本功能不能继续扩大。

只读目录、权限变化、磁盘满、轮转或清理失败，均进入 degraded 状态。后台每 30 秒最多尝试一次恢复；恢复成功后记录失败区间与累计丢弃数量。日志模块不修改业务数据，也不阻止已有应用正常运行。

## 异步写入与故障处理

LOG-15：日志生产者只做有界字段处理与非阻塞入队；文件 IO、轮转及清理在专用后台线程执行。普通队列最多 1024 条，另有 64 条 ERROR 保留队列；每条已经受 16 KiB 限制，不能使用无界字符串缓冲。

队列满时丢弃对应新记录并增加计数；ERROR 不被 INFO 挤出，但 ERROR 保留队列也满时仍允许丢弃。正常写入恢复后发出 diagnostics.dropped 汇总，不逐条重复报告。文件 IO 故障不通过同一队列递归打日志；最小固定错误提示可发往 stderr，诊断状态保留在内存。

正常运行时每 1 秒至多一个周期主动 flush；写出 ERROR 后及时 flush。正常退出最多等待 2 秒排空已接收队列并 flush，超过时明确记录或暴露未完成状态，不无限延迟退出。flush 不承诺断电持久性。

LOG-16：在数据库打开、插件注册、会话恢复之前完成日志初始化。目录尚未解析时仅使用有界启动缓冲，解析成功后按序写入；解析失败则使用固定、无敏感内容的 stderr 提示，不擅自落到工作区或公共临时目录。无法创建文件时，UI 可用后显示日志不可用原因。

panic hook 不依赖普通队列或 SQLite，也不获取可能已被 panic 线程持有的日志锁；尝试通过预先准备的应急通道保存最小 app.panic。没有可用通道时只输出安全提示，不再次 panic。panic 原始 payload 不得透传给旧 hook 后进入文件。启动失败和 panic 必须在子进程测试中观察实际文件，而非仅验证函数返回。

正常结束证据只能在退出流程已完成时写入。记录上次状态的有界元数据必须区分仍存活的并行进程与已结束进程；不把另一正在运行的实例判为异常退出。元数据缺失或损坏时状态为未知，不能因此修改会话状态。SIGKILL、进程强制结束、断电、native abort 和部分 OOM 无法保证生成 panic 或最后一条日志。

LOG-17：前端同一异常指纹每 10 秒最多接受 1 条，每窗口在滚动的 60 秒内最多接受 60 条（使用单调时钟）；被抑制数量进入汇总。指纹由允许的事件类别与安全位置生成。原生侧执行限流，页面不能通过改变 error message 绕过；报告失败不得再次上报自身失败而循环。

## 用户入口

LOG-18：在固定宿主“设置 → 运行与诊断”增加“应用日志”区域，显示当前 profile 的保存位置、正常或降级状态、最近写入失败的本地化原因和累计丢弃数量。状态读取仅观察日志模块，不查询或启动插件。

“打开日志文件夹”由原生宿主打开固定 DATA/logs 目录。IPC 不接受任意路径；目录尚未创建或不可用时给出明确反馈。此操作不打开每个文件，不清空目录，也不隐式上传。

内置 Material 3 与 ak-ui 的浅深主题、窄窗口、键盘访问均可使用此入口。外部工作台故障或恢复默认呈现后入口仍可达。现有插件依赖与登录检查状态继续来自共享状态，不增加独立检查或改变刷新语义。

## 后续诊断模式与导出

LOG-19 属于 L2：用户可为固定模块列表开启 DEBUG，使用单调时钟计时，30 分钟后自动关闭，可提前关闭。重启恢复默认级别，不永久保存开启状态；多窗口展示同一原生状态。RUST_LOG 不扩大文件可记录的字段或来源。新增 DEBUG 事件也必须登记允许字段。

LOG-20 属于 L2：用户选择最近 1 小时、24 小时或 7 天，通过原生保存对话框导出 ZIP。包内只有经过校验的诊断 JSONL 和 manifest.json；manifest 含按 boot_id 关联的应用版本、构建渠道、系统类型与架构，以及时间范围、实际覆盖范围、缺失或截断计数和各文件校验值。运行环境取自实际导出的记录，不能统一替换成执行导出的应用版本；同一 boot_id 的环境字段冲突时导出失败并报告数据损坏。禁止包含数据库、聊天历史、附件、环境变量、认证文件、插件私有文件和原始 stderr。

导出从日志读取稳定前缀，逐行重新验证字段，只忽略不完整尾行；非法中间记录跳过并计数。采用流式处理，总解压后内容不超过 100 MiB，达到上限保留较新完整记录并注明截断。不暂停会话；失败或取消不留下被报告为成功的半成品。没有日志时说明无可导出内容。包内使用相对安全文件名，不含本机路径。用户自行分享，应用不自动发送。

| 可信前端异常入口与呈现桥 | 提取允许的位置、调用受限 IPC | 原有错误展示与恢复、外部呈现隔离、工具页权限 |
| 应用层诊断控制器与设置组件 | 日志状态、目录操作、后续 DEBUG 与导出 | 业务控制器不依赖具体 UI Kit；固定宿主入口继续可达 |
| 测试与探针 | 注入时间、文件故障、容量与进程故障，读取实际输出 | 使用隔离数据和临时工作区，不更改用户现有日志或数据库 |

技术实现沿用 tracing，但新增事件 sink 必须满足 LOG-11。可以复用 tracing-appender 的后台写入与时间轮转；仅有按天轮转和文件数量限制不满足本规格的大小、年龄与总容量要求。具体依赖与线程方案由实现选择，不能改变上述可观察行为。

## 验收矩阵

每个用例必须保存可复现的输入、命令、断言和结果。自动化优先断言实际 JSONL、文件大小、业务状态与界面动作，不以源码字符串或函数是否存在代替行为验证。时间和小容量可通过测试专用依赖注入加速；生产构建不能由不可信 IPC 修改这些限制。

| 用例 | 对应要求 | 操作或故障注入 | 通过条件 |
| --- | --- | --- | --- |
| T01 | LOG-01、LOG-02、LOG-16 | 隔离数据启动并正常关闭；分别使数据库打开、迁移、插件注册失败 | 正常启动有阶段顺序、ready 和 stopped；各失败只有对应 stage 的 startup.failed，日志早于失败可用 |
| T02 | LOG-03、LOG-16 | 正常退出后重启、强杀后重启、两个实例并行启动、破坏运行元数据 | 仅有可信未正常结束证据的已结束运行产生 previous_exit_unknown；活进程无误报；损坏不改变业务状态 |
| T03 | LOG-04、LOG-10、LOG-11、LOG-16 | 子进程触发含测试秘密的 panic，分别在普通运行和普通队列饱和时触发 | 可写磁盘上产生可解析的最小 app.panic，单独读取应急记录也能确定运行环境；无秘密和原始 payload；子进程退出不死锁 |
| T04 | LOG-05、LOG-06 | 假插件正常握手、启动失败、超时、非法响应、主动停用、意外退出 | 对应事件、身份及退出原因准确；预期停止不报意外崩溃；内置与第三方一致 |
| T05 | LOG-07 | 创建、恢复、发送、取消；注入旧 generation 响应与结果未知 | 事件关联正确；请求完成不冒充回合完成；旧响应仍被原有门禁拒绝，绑定与投递证据不变 |
| T06 | LOG-08、LOG-12、LOG-17 | 真实页面触发 error、unhandledrejection、呈现故障并连续重复 | 原生文件可观察到受控事件；数量受限且有汇总；原有错误展示和恢复可用；报告失败无循环 |
| T07 | LOG-10 | 写入中文、换行、控制字符、16 KiB 边界、超长身份、未知字段；回拨墙钟 | 完整行均解析成功，单行不超限且包含必填运行环境字段，身份不被截断冒用，无注入假行；sequence 与 elapsed_ms 合规 |
| T08 | LOG-11、LOG-12 | 将唯一 canary 注入 token、Cookie、嵌套对象、错误链、panic、聊天、路径、stderr、终端和 URL 参数 | 搜索所有 JSONL、应急文件与运行元数据均无 canary；未知字段被丢弃；正常允许字段仍可读 |
| T09 | LOG-12 | 非可信页面调用诊断 IPC；伪造窗口、级别、事件名、session_id、文件路径 | 原生拒绝或移除伪造字段，无越权文件与事件；可信窗口正常报告；工具页权限不扩大 |
| T10 | LOG-13 | 分别启动开发与正式 profile；同日重启；制造 UTC 换日和单文件边界 | 数据目录隔离，无覆盖；单文件不超 10 MiB，完整事件写入新分片；使用实际字节计数 |
| T11 | LOG-10、LOG-14 | 人工时间与封存文件跨 14 天边界；填满 100 MiB；增加同时间分片；同一运行持续写入，分别由年龄和容量规则清理包含 app.starting 的分片 | 到期规则、排序和容量均符合规格；计入当前及应急记录；删除范围仅为受管普通文件；启动分片清理后，仅凭任一剩余完整记录仍能确定该运行的应用版本、构建渠道、系统类型与架构 |
| T12 | LOG-13、LOG-14 | 同 profile 两进程并发写入清理；锁住旧文件；放置未知文件与指向外部的链接或 junction | 不覆盖或删除活动文件，不越界，不触碰未知文件；无可回收容量时停止增长并显示降级 |
| T13 | LOG-09、LOG-14、LOG-15 | 注入权限拒绝、磁盘满、写入与删除失败，再恢复 | 应用仍可完成原有业务动作；状态显示错误；最多每 30 秒一次恢复尝试，恢复后汇总丢弃 |
| T14 | LOG-09、LOG-15 | 暂停后台 writer，填满普通及 ERROR 队列，随后解除 | 生产者不等待磁盘；1024 与 64 队列边界成立；丢弃计数准确；正常恢复产生汇总，无递归增长 |
| T15 | LOG-15、LOG-16 | 正常关闭有待写事件的进程；用可控 writer 模拟永久阻塞 | 正常场景退出后已接收事件完整；阻塞场景收尾最多等待 2 秒且不声称排空成功 |
| T16 | LOG-18 | 两套内置皮肤浅深、窄窗口和键盘；外部工作台故障；真实桌面打开日志目录 | 状态与本地化正确、入口可达、只打开当前 profile 目录；无任意路径参数；不触发插件检查或登录 |
| T17 | LOG-19，L2 | 多窗口开启、提前关闭、推进 30 分钟、重启、设置 RUST_LOG | 同步状态、按时失效、重启关闭；默认与 DEBUG 下均通过 T08 内容限制 |
| T18 | LOG-10、LOG-20，L2 | 导出各时段；轮转并发、损坏行、半行、容量上限、取消、写出失败；导出范围排除启动事件并含不同版本的多个 boot_id；注入同一 boot_id 的环境字段冲突 | ZIP 与 manifest 一致，仅含允许文件；各运行环境来自对应保留记录，启动事件缺失不影响识别，环境冲突明确失败；范围和缺失明确；无秘密和半成品成功反馈 |

T08 必须在普通文件层和 panic 应急层分别注入；不得只验证一个脱敏函数。T06 的浏览器替身测试只证明前端行为，必须补原生 IPC 到实际文件的端到端证据。

## 实施顺序与完成门槛

1. L1a：实现 schema、允许字段、文件与队列、轮转清理、启动与退出和 panic。先通过 T01–03、T07–08、T10–15。
2. L1b：接入插件和会话关键边界、可信前端异常与设置入口，通过 T04–06、T09、T16，并重跑共享路径的内容限制与故障降级。
3. L2：增加临时 DEBUG 与导出，实施时执行 T17–18 并重跑受影响的 L1 用例。

每步交付必须运行仓库根目录的 pnpm run verify。原生持久化变化运行相应 Rust 测试；启动、退出、插件或会话生命周期跨模块变动运行完整命令：

```sh
pnpm run verify
cargo test --manifest-path src-tauri/Cargo.toml --lib
```

受影响的现有回归至少选取 [SessionHost 测试](../src-tauri/src/session_host_tests.rs)、[运行诊断测试](../test/runtime-diagnostics.test.mjs)和[运行诊断浏览器探针](../probes/runtime-diagnostics-browser.mjs)，再按[回归矩阵](plugin-boundaries-and-regression.md#regression-gate)取并集。新增日志测试与桌面探针的实际命令在实现提交中登记。

Windows 桌面打包运行须验证无控制台时仍落盘、目录打开、进程退出和 junction 边界。macOS、Linux 的原生结果分别登记；未执行的平台明确标为未验证，不用浏览器替身或跨平台编译代替。测试证据只含合成内容、临时身份与隔离路径。

完成报告按 T 编号列出通过、失败或未执行及原因，并列出实际文件路径和命令。L1 的 T01–16 未全部通过时，不能标记 L1 完成；平台验证范围随结果单独说明。仅编写本规格不改变现行合同，也不代表上述验收已经通过。
