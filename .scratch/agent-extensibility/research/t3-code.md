## Agent 如何接入

T3 将**驱动类型**（实现哪一种协议）和**提供方实例**（用户选择的具体配置）分开。编排层按实例寻找适配器，调用统一的 `ProviderAdapterV2` 查询能力、规划配置变更、打开运行时。运行时负责建立和续接原生会话、开始或中断轮次、回应审批等请求，按实现提供历史注入等可选操作。同一种驱动可配置多次，能否隔离账号取决于 Agent 自己的凭据存储。v0.1.11 的注册表有十个具名驱动，另有一个通用 ACP Registry 驱动。[注册表](https://github.com/pingdotgg/t3code/blob/v0.1.11/apps/server/src/provider/builtInDrivers.ts#L22-L46) · [适配器接口](https://github.com/pingdotgg/t3code/blob/v0.1.11/packages/provider-core/src/server/ProviderAdapter.ts#L709-L837) · [实例与隔离约束](https://github.com/pingdotgg/t3code/blob/v0.1.11/docs/internals/providers.md#L3-L25) · [ACP 账号边界](https://github.com/pingdotgg/t3code/blob/v0.1.11/docs/user/providers-acp.md#signing-in)

**协议与工具承担不同职责。** ACP 或专用适配器负责驱动 Agent。注入到会话的 T3 MCP 工具则让 Agent 反过来读取工作台数据。OpenCode 说明了这个区别的实际后果。其原生服务按目录注册 MCP，而 T3 要把工具连接绑定到线程。对 T3 托管的 1.x 聊天服务，T3 为每个线程启动一个服务。2.x 每个实例用一个服务，每个线程注册独立工具名，并在该会话的权限规则中拒绝其他线程的工具。外部服务的工具能力还取决于部署方式。这些结论针对 OpenCode 的服务接口，aibo 采用的 `opencode acp` 需要独立验证。[隔离实现说明](https://github.com/pingdotgg/t3code/blob/v0.1.11/docs/internals/providers.md#process-and-account-isolation) · [OpenCode 用户说明](https://github.com/pingdotgg/t3code/blob/v0.1.11/docs/user/providers-opencode.md#local-or-external-server) · [aibo 的 OpenCode 验证计划](../map.md)

## 两种上下文传递

| | 在 B 的消息中引用 A | 同一个 T3 线程由 A 切换到 B |
| --- | --- | --- |
| 用户操作 | 输入 `@` 和线程标题、拖入侧栏线程，或粘贴 **Copy thread** 得到的链接。 | 在模型选择器改用另一提供方，再发下一条请求。仅在正文里提及 `@opus` 等模型名不会触发切换。 |
| 一开始给 B 什么 | 标题、`environmentId`、`threadId` 和按需读取说明。B 能用 `t3_thread_read` 读消息或活动，按位置翻页、按条目及文本偏移补齐长输出。 | 当前请求，加上工作台从当前 T3 线程挑出的历史。本地保存覆盖的轮次、来源及目标原生线程、所选和遗漏条目的信息。 |
| 以后读到什么 | 普通线程引用按读取时的源记录取数，结构中没有用户圈定的起止消息。链接机器上的线程也可按引用访问。 | B 初次参与时从可见历史选取；返回曾参与的 A 时，通常续接 A 的原生线程，仅补 A 离开后的轮次。A、B 各自的原生状态仍由各自管理。 |

**跨环境有一个重要例外。** 来源位于另一台未链接的环境时，粘贴得到普通链接。通过拖放，T3 可以从在线且兼容的来源导出当时的可见记录和已保存的文本上下文，作为 transcript 文件附上。此后来源离线也能读该文件。后续消息和历史附件的文件内容不随之复制。这才是 T3 这里的快照路径。[跨环境拖放](https://github.com/pingdotgg/t3code/blob/v0.1.11/docs/user/composer.md#L359-L365)

### 切换时具体带走什么

1. 编排层从工作台已保存的可见轮次取材，过滤已回滚轮次和取消的排队消息。候选类型包括用户与助手消息、命令及退出码和输出、错误、中断结果、文件变更的路径、计划 Markdown。未进入该列表的类型跳过。中断或失败前已写出的可见工作也能交接。[条目转换](https://github.com/pingdotgg/t3code/blob/v0.1.11/packages/provider-core/src/server/handoffBudget.ts#L135-L177) · [可见性过滤](https://github.com/pingdotgg/t3code/blob/v0.1.11/apps/server/src/orchestration-v2/ContextHandoffService.ts#L132-L147) · [用户说明](https://github.com/pingdotgg/t3code/blob/v0.1.11/docs/user/portable-handoffs.md)
2. 在预算内依次尝试最近一条用户记录、最近一条 assistant 角色记录、第一条用户记录，然后从近往远填满剩余空间。选中条目按原顺序交付，保留角色、状态和来源标识；过长条目整条省略，附覆盖范围与遗漏标识供 MCP 补读。历史图片和附件内容、内部推理、可执行工具状态及审批状态不会移植。默认初始上限 16,000，实际还会为当前输入及附件、已有上下文、工具和后续工作留量，当前用户请求保持完整。[选择与预算](https://github.com/pingdotgg/t3code/blob/v0.1.11/packages/provider-core/src/server/handoffBudget.ts#L224-L292) · [预算规则](https://github.com/pingdotgg/t3code/blob/v0.1.11/docs/user/portable-handoffs.md#context-limits)
3. Codex 支持时，适配器调用 `thread/inject_items` 把历史按角色写进目标原生线程，再发送本轮请求。收到明确的“方法不存在”错误时可退回内联方案。其他走内联路径的适配器会在本轮用户文字前收到带来源标记的历史。系统记录交付状态和条目 ID，遇到交付结果不确定时避免将同一批历史重复写入原生线程。目标原生上下文已满时，满足恢复条件可用新原生线程和有界历史自动续接。[Codex 注入与错误分支](https://github.com/pingdotgg/t3code/blob/v0.1.11/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts#L8156-L8182) · [交付代码](https://github.com/pingdotgg/t3code/blob/v0.1.11/apps/server/src/orchestration-v2/ContextHandoffDelivery.ts) · [恢复规则](https://github.com/pingdotgg/t3code/blob/v0.1.11/docs/user/portable-handoffs.md#context-limits)

同一版本里，旧的内部说明仍写着“每项 240 字符”。切换提供方的实际入口 `prepareProviderHandoff` 调用 `historicalMessage`、`selectHistory`、`renderHistory`，预算测试还专门覆盖了超长多语言条目整条省略。240 字符压缩函数仍用于某些简述，例如 fork 合回的展示文字，不能据此描述给新 Agent 的整份输入。上面的行为按实际代码和该版用户指南核对。[旧内部说明](https://github.com/pingdotgg/t3code/blob/v0.1.11/docs/internals/context-handoffs.md) · [发布版交接实现](https://github.com/pingdotgg/t3code/blob/v0.1.11/apps/server/src/orchestration-v2/ContextHandoffService.ts#L483-L566) · [上游预算测试](https://github.com/pingdotgg/t3code/blob/v0.1.11/apps/server/src/orchestration-v2/ContextHandoffBudget.test.ts#L113-L200)

## 邻近功能

- **引用一段回答。** Assistant citation 把选中的原文和来源标识写入消息，即使原消息改变或消失，已保存的引文仍能用。回复某条回答的上下文记录还可带开头和精确 `itemId` 供读取全文。两者分别解决“保留这句话”和“回到这一条”，都与引用整个线程有区别。[引文设计](https://github.com/pingdotgg/t3code/blob/v0.1.11/docs/internals/assistant-citations.md#L1-L16) · [回复记录](https://github.com/pingdotgg/t3code/blob/v0.1.11/packages/shared/src/composerContextReferences.ts#L353-L369)
- **Fork 与合回。** fork 创建新 T3 线程，记下来源位置；首次发送时再根据目标能力决定原生 fork 或可移植历史。显式 merge-back 将子线程的增量交给目标，保留来源、范围与目标轮次。[线程关系与解析](https://github.com/pingdotgg/t3code/blob/v0.1.11/docs/orchestration-v2/thread-lineage-and-context-transfer.md#lazy-resolution) · [合回交接实现](https://github.com/pingdotgg/t3code/blob/v0.1.11/apps/server/src/orchestration-v2/ContextHandoffService.ts#L408-L482) · [合回集成测试](https://github.com/pingdotgg/t3code/blob/v0.1.11/apps/server/src/orchestration-v2/testkit/ThreadMergeBack.integration.test.ts#L249-L255)
- **侧聊。** `/side` 或 `/btw` 在同一目录里开支线提问，主线程可继续工作。侧聊的 **Add to chat** 把引用放回主输入框，由主 Agent 按需读取；它与显式的 fork 合回是两条路径。官方还指出外部 OpenCode 服务上的 Agent 无法读取该侧聊链接。[侧聊操作](https://github.com/pingdotgg/t3code/blob/v0.1.11/docs/user/thread-sidebar.md#side-chats)
- **委派。** 工作台 MCP 的 `delegate_task` 允许选择目标提供方，子 Agent 启动时只接收任务描述，可使用独立 worktree。父 Agent 可取回结果或取消。Agent 自身启动的原生子任务另有事件与能力约束，普通 ACP 没有可移植的原生子任务父子关系契约。[委派工具](https://github.com/pingdotgg/t3code/blob/v0.1.11/apps/server/src/mcp/toolkits/orchestrator/tools.ts#L74-L123) · [通用 ACP 的边界](https://github.com/pingdotgg/t3code/blob/v0.1.11/docs/user/providers-acp.md#permissions-and-terminals)

- **代码审阅与交付。** 线程可以使用独立 Git worktree。按轮次查看 diff 时，T3 会区分本轮编辑与 pull、merge 或 rebase 带入的改动。用户也可以查看分支差异、提交、推送、创建 PR；Issues 页面把 GitHub、GitLab、Linear 等跟踪器的事项接到这条工作流。[代码审阅](https://github.com/pingdotgg/t3code/blob/v0.1.11/docs/user/source-control.md#review-turn-changes) · [发布记录](https://github.com/pingdotgg/t3code/releases/tag/v0.1.11)
- **多端与远程执行。** Agent、工作区、Git 和终端位于环境服务器，桌面、网页和手机共享线程。用户可以在手机审批桌面启动的工作，通过应用内浏览器预览远端开发服务，也可以转发端口到本机。[架构](https://github.com/pingdotgg/t3code/blob/v0.1.11/docs/internals/overview.md) · [用户指南](https://github.com/pingdotgg/t3code/blob/v0.1.11/README.md#what-you-get) · [浏览器隧道](https://github.com/pingdotgg/t3code/releases/tag/v0.1.11)

## 对 aibo 的取舍

1. **优先验证“第三个 Agent 能读既有快照”。** 以 Claude 已产生的一段工具输出为例，在 OpenCode 会话里送出其引用，再给源会话追加消息。验证 OpenCode 能按页读取原文、看不到新消息，同时验证同目录另一个未被授予该引用的会话无法读取。这个场景同时检验 MCP 注入、会话身份和快照边界。aibo 已定义固定标题与连续消息范围、随引用携带概要，源会话删除后引用失效；T3 的线程链接和 transcript 文件各只覆盖其中部分语义。[aibo 术语表](../../../GLOSSARY.md) · [ADR 0002](../../../docs/adr/0002-references-are-snapshots.md) · [隔离议题](../issues/03-session-isolation.md)
2. **把“可配置接入”和“该 Agent 能做什么”分开验收。** 可以借用 T3 对驱动与实例的区分，让多份命令配置复用 ACP 客户端；模式、续接、审批、中断、额外可读目录和 MCP 传输逐项用握手或实测确认。尤其应分开验证“能读引用快照”与“能只读访问源工作区”。采集本机 Agent 真实协议帧，覆盖首次发送、重启续接、等待审批时中断、同目录双会话等场景。T3 的 OpenCode 服务隔离案例可以产生测试问题，实测结果才能决定 aibo 的 ACP 进程粒度。[T3 接入与测试规范](https://github.com/pingdotgg/t3code/blob/v0.1.11/docs/internals/adding-a-provider.md#tests) · [aibo 接入决策](../../../docs/adr/0001-drive-the-agents-own-clis.md) · [原生权限模式](../../../docs/adr/0003-agents-own-permission-modes.md) · [能力议题](../issues/04-capabilities.md)
3. **把“换 Agent 接着做”作为独立产品决定。** 按 aibo 当前定义，会话属于一个 Agent。现有模型已经能在另一个 Agent 的会话中打开固定范围的引用，原会话仍有自己的时间线。若以后想让多个 Agent 共用一条可见时间线，需要明确每轮归属、原生会话与覆盖范围、首次切换和切回的历史预算、失败重试及用户如何辨认实际传给新 Agent 的内容。T3 的交付记录和按条目补读可作为设计参照，这一决定不必成为接入第三个 Agent 的前置条件。[aibo 术语表](../../../GLOSSARY.md) · [当前接入范围](../map.md) · [T3 切换决策](https://github.com/pingdotgg/t3code/blob/v0.1.11/apps/server/src/orchestration-v2/Orchestrator.ts#L9005-L9092) · [T3 交付记录](https://github.com/pingdotgg/t3code/blob/v0.1.11/apps/server/src/orchestration-v2/ContextHandoffDelivery.ts)
