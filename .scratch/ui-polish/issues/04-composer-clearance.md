# 04: 消息底部留白跟随输入区

Status: resolved

**What to build:** 不管输入区上方叠了多少东西，最后一条消息都不会被输入区挡住；输入框有最大高度。

现状：
- 消息列表底部留白固定 170（`internal/shell/view.go:258`）。输入区是绝对定位的一列：横幅、未开始的审批卡、徽章行、草稿上的芯片、多行草稿，加起来常常超过 170，最后几条消息就压在输入区下面。
- 输入框只有 `MinHeight(44)`，没有最大高度（先核实：粘贴长文时会不会一直长高）。

- [x] 底部留白取输入区上一帧的高度（`composer.Bounds().H`）加 16 左右；高度变化时，若列表在跟随底部（`FollowEnd`），保持贴底
- [x] 输入框最大高度约为窗口高度的 40%，超出在框内滚动
- [x] Tester：归档横幅加 8 行草稿、再加到 68 行草稿时，最后一条消息仍在输入区上方；草稿不超过窗口的 40%

## 不做

- 横幅本身怎么合并（13）。

## 实现说明

- `sessionView.composerHeight` 记下输入区那一列（横幅、未开始的审批、徽章行或选择栏、输入卡片）上一帧的高度。高度变了就记下来，再用 `c.After(0)` 要一帧，让消息列表在下一帧用新的留白。
- 消息列表的底部留白改为 `bottomRoom`：输入区高度加上它离窗口底边的 16 和上方的 16；第一帧还不知道高度时仍用 170。
- 列表在跟随底部（`FollowEnd`）时，留白变大后仍然贴底，不用另外处理。
- 输入框加 `MaxHeight(draftMaxHeight(c))`：窗口高度的 40%（不低于 44），超出后在框内滚动。
- 测试 `TestComposerClearance`（新文件 `composer_layout_test.go`）：12 轮对话的已归档会话，草稿 8 行、再加到 68 行，检查最后一条回复的底边在归档横幅之上，以及输入框高度不超过窗口的 40%。改回固定 170、去掉最大高度时，这个测试在三处失败。

## 没有验证

- 输入区高度变化后，消息要晚一帧才让出空间，这一帧里最后一条消息可能被挡住一下。没有运行应用看过。
- 用户往上翻看时（不跟随底部），留白变化会不会让视野跳动：没有测。
- 只测了归档横幅和长草稿；审批卡、多个横幅同时出现走的是同一条路径，没有单独测。
- `go test -race`：这台机器没有 gcc。
